# MySQL 日志增量与指定时间点恢复

MySQL 任务可以开启 **MySQL 日志增量 / 指定时间点恢复（PITR）**。首次和全量间隔到期时创建 `mysqldump` 全实例基线，其间归档**自该基线以来**的原始 binlog。每份日志归档只依赖一份全量，不依赖中间日志备份记录。恢复会自动下载并校验基线与日志，再按顺序应用。

这是逻辑全量加 binlog 的恢复方案，不是 XtraBackup / MariaBackup 物理增量。当前兼容范围为 MySQL 8.0 / 8.4，执行节点需安装 MySQL 8.0.26+ 的 `mysql`、`mysqldump`、`mysqlbinlog` 客户端。MariaDB 不在此模式兼容范围内。

## 配置

1. 新建 MySQL 任务，填写数据库主机、端口和备份账号。
2. 在策略步骤开启 PITR，数据库名称设为 `*`，表示整个实例。为保证跨库事务正确性，PITR 不提供单库筛选。
3. 选择固定执行节点（Master 或 Agent）；不支持节点池动态切换。
4. 设置全量间隔，默认 24 小时，可设置 1–720 小时。计划执行频率决定 binlog 的归档间隔。例如每 5 分钟运行一次，正常情况下 RPO 约为 5 分钟加任务耗时。
5. 配置存储目标、压缩、加密和保留策略。远程加密需要同时升级 Master 和 Agent。

数据库必须开启 `log_bin`，使用 InnoDB。全量期间避免 DDL；非事务表无法保证一致性。备份账号除了常规 mysqldump 所需权限，还需查询日志位置、短暂读取锁和复制读取所需权限（通常包括 `REPLICATION CLIENT`、`REPLICATION SLAVE`、`RELOAD`，实际权限按数据库版本配置）。恢复账号必须拥有创建/覆盖全实例对象及设置 `sql_log_bin` 的权限。请给 Agent 到 MySQL 的网络连接配置可信网络或数据库 TLS 隧道。

恢复窗口内请勿执行 RESET MASTER / RESET BINARY LOGS AND GTIDS 或重新初始化实例；这会使旧日志坐标失效。

源端 binlog 保留期必须大于全量间隔、归档间隔和最大故障恢复时间之和；系统不会修改数据库保留参数，也不会自动清除源端 binlog。源日志被清理、日志编号不连续或服务器 UUID 变化时，本次归档失败，不会伪装成可恢复的备份。修复源端保留策略后，可等待下一次周期性全量，或新建 PITR 任务建立基线。

## 恢复

在成功的 **MySQL binlog** 记录详情点击恢复，可输入带时区的 RFC3339 时间，例如 `2026-11-14T12:30:00+08:00`。界面展示本条归档的可恢复范围。时间须在基线完成至日志截止之间，不包含截止秒；留空则恢复到记录捕获的日志位置。

时间统一转换为 UTC，重放使用 `mysqlbinlog --stop-datetime`；它应用目标时间之前的事件，目标秒及其后事件不应用。时间分辨率为秒，不承诺亚秒精度。恢复窗口截至**已成功归档**的日志，不包含归档后的源端事务。

恢复覆盖任务当前配置的**整个实例**，包括数据库与账号等系统对象。建议先把任务连接改到隔离的恢复实例，并实际验收业务数据。恢复不是事务性的，失败不自动回滚已导入的数据。当前不支持自动验证演练，应定期在隔离实例恢复并检查业务结果。

API 使用现有 `POST /api/backup/records/:id/restore`，请求体可增加 `restoreTime`：

```json
{"restoreTime":"2026-11-14T12:30:00+08:00"}
```

自动保留和手动删除都会保护仍有日志备份依赖的全量基线，因此实际保留量可能超过最大份数。先删除或过期其日志记录后，基线才能清理。

## 密钥与升级

远程 Agent 仅获取记录专属派生密钥，新远程加密归档采用 `BXENC2`，包含记录身份、分块顺序与完整结束标记的认证。Master 仍可读取旧 `BXENC1` 归档。请保存 Master 配置加密密钥；仅保存备份文件而丢失此密钥无法恢复。该功能不轮换密钥，不自动处理旧主密钥迁移。
